# 統計モードの共通化の修正計画（指標の性質・標本の順序・失敗の扱い）

作成: 2026-11-01（ローカル `44b3fc5` 時点）

実装で計画と変えた点:
- やり直しは、orchestrator がキューに戻す（決定 1）を、キュー自身が行う形で実装した（ワーカーは完了時に状態を報告するので、どの戦略でも同じ仕組みで済む）。試行番号と理由は記録の meta（`attempt_id`、`retry_reason`）に入り、dataset CSV にも列として残る。
- fixture（記録済みの結果の解釈し直し）はやり直さない（同じ結果になるため）。
- PRISM の `steps_to_failure_capped` の範囲は [0, steps + 1]（失敗しない経路は horizon + 1 になる。`trace_parser.py`）。
- 先行して入れた `unbounded_metrics` は互換のため残し、`metric_specs` の `real` と同じ扱いにした。
- 指標の宣言を持たない対象（統計の profile が無い対象、宣言していない指標）は、今どおり検査しない。
- 失われたケースの報告として、orchestrator の要約に `retried_cases` と `abandoned_cases` を足した。
- 欠けの判定は「番号 1 から最後まで」ではなく「戦略が実際に発行した番号」をたどる（PRISM の DKW 戦略は番号を 0, 2, 4, … と 1 つおきに付けており、番号の付け方は変えないため）。
- AWSIM の GP 探索の各モード（`binomial_mode.py` などの runner）は、記録を別の経路で読むので、この整理はまだ通していない（保証は今どおり「なし」）。

## 1. 目的

重点サンプリングで入れた 3 つの仕組みを、他の統計手法（二項区間、SPRT、DKW、EBStop。旧来の `--mode` と `--stopping-rule` の両方）
にも入れる。

| | 内容 | 今の問題 |
|---|---|---|
| A | 指標の性質を対象が宣言し、手法との組み合わせと値を共通基盤が検査する | EBStop の値の範囲は CLI の既定値（0〜10、`orchestrator.py:162`）で、範囲外の値を検査しない（`evaluation/ebstop.py`）。0/1 や連続値の前提も検査しない |
| B | 番号順に連続した標本だけで判断する | 旧来の `--mode` は届いた順に、`--stopping-rule` は番号で並べ替えたうえで欠けを飛ばして使う。クラスターでは早く終わる回（衝突など）が判断に多く入り、推定が偏る |
| C | 失敗した点を同じ点で 3 回までやり直し、すべての試行と失敗を記録・報告する | 成功した回だけを黙って使う（例: `evaluation/binomial_ci.py:39`）。失敗の件数は保証の判断にも報告にも入らない |
| D | 失われたケースを出し直す（B の前提） | 実行中のワーカーが死ぬと、そのケースは再発行されず、orchestrator は終わらない。B を入れると、欠けた番号で判断も止まる |

範囲外: AWSIM の GP 探索の標本（`ADAPTIVE`）に保証を与えること（今どおり「保証なし」と表示する）。

## 2. 守ること

- 手元で 1 件ずつ実行した場合（インラインのワーカー）の判断と数値は変えない。届く順が番号順なので、B は何も変えない。
  確かめ方: `tests/fixtures/architecture/decision_traces.json`（判断の記録）、`target_snapshot.json`、被覆率の基準テスト、
  smoke テストが変更なしで通ること。判断の記録は、2026-11-01 の EBStop の修正（`3929a02`）で `awsim:ebstop` の 1 件だけを外した
  （範囲のない `min_ttc` への EBStop が実行前のエラーになったため）。これを基準とする。
- 例外: A の値の検査で外れた値が見つかる場合と、C の報告項目の追加。どちらも、報告（diagnostics）に項目が増えるだけで、
  既存の値は変えない。既存の対象と設定で外れた値が見つかったら、計画を止めて相談する。

## 3. 設計

### 3.1 共通の入り口: 標本の表を整える 1 つの関数（B・C）

すべての統計サービスの `evaluate_request(data, request)` は、データの表（dataset CSV から読んだもの）を受け取る。
その直前に通す共通の関数 `prepare_statistical_sample`（新規 `evaluation/statistical_sample.py`）を置き、次をそろえる。

1. 順序: 標本の番号（`sample_index`。無ければ `global_loop_num` / `loop_num`）で並べる。
2. 重複: 同じ番号の行は、最初に届いたものだけを使い、残りは件数を報告する（D の出し直しで生じうる）。
3. 接頭部: 番号 1（再開時は最初の番号）から欠けずにそろった部分だけを残す。欠けた番号が「実行中」なら、そこで切る。
   欠けた番号が「実行中でもない」（失われた）なら、D の出し直しを待つ。出し直しも尽きた番号は、欠損として報告し、
   その後の標本も使うが、結果の保証は「近似」に下げる。
4. 失敗: 接頭部の中の失敗（`status != success`）を数え、失敗の扱い（3.3）に従う。
5. 報告: 使った件数、切った位置、待っている番号、重複・欠損・失敗の件数を、報告（diagnostics）の `sample` に入れる。

実行中かどうかは、orchestrator が持つキューの状況（`get_in_flight_tasks`）から、戦略を通して渡す。手元実行では常に空なので、
接頭部 = 届いた全部となり、今と同じ。

AWSIM の探索の標本（番号は `global_loop_num`）にも同じ順序と接頭部を使う（保証は今どおり「なし」）。

### 3.2 指標の性質の宣言（A）

`StatisticalTargetProfile` に、指標ごとの性質 `metric_specs` を足す（新規 `contracts/metric_spec.py`）。

| 種類 | 意味 | 使える手法 |
|---|---|---|
| `binary` | 値は 0 か 1 | 二項区間、SPRT |
| `bounded(lower, upper)` | 値は [lower, upper] に入る | EBStop、DKW |
| `real` | 実数（範囲の保証なし） | DKW（分位点） |

- 実行前: 共通基盤が、選んだ手法と指標の種類が合うかを確かめる（例: EBStop には `bounded` が要る）。合わなければエラー。
- 評価のたび: 3.1 の関数が値を確かめる。宣言の外の値（`binary` に 0/1 以外、`bounded` に範囲外、無限大）があれば、
  区間を出さずにエラーで止め、件数を報告する（決定 5。EBStop で先に入れた扱いに統一する。宣言の外の値は、対象の解釈器か宣言の誤り）。
- 先行して入れた `unbounded_metrics`（2026-11-01、`3929a02`）は、この宣言の `real` に置き換える（`unbounded_metrics` は
  `real` の指標の一覧から作る互換の名前として残す）。
- EBStop の範囲: 宣言の範囲を使う。CLI の `--ebstop-value-range-min/max` は、宣言の範囲を狭めることだけを許す
  （広げると保証が崩れるため）。宣言の無い対象は今どおり CLI の値を使い、報告に「対象の宣言なし」と出す。
- 各対象の宣言（案。値は各対象の指標の定義を見て確かめる）:
  - AWSIM: `c_collision` は `binary`、`min_ttc`・`min_distance`・`min_ttb` は `real`（上限が無いので EBStop には使えない）
  - dynamics: `c_collision` / `c_event` は `binary`、`min_ttc` は `real`
  - PRISM: `c_failure` は `binary`、`steps_to_failure_capped` は `bounded(0, steps)`（`steps` は実行時の設定なので、宣言は設定から
    範囲を計算する関数にする）
  - bernoulli: `c_failure` は `binary`、`time_to_failure` は `real`、`score` は `bounded(0, 1)`

### 3.3 失敗した回の扱い（C）

決定（2026-11-01）: 実行できるかを判定する式は使わない。実行できなかった点は、同じ点で 3 回まで実行し直し、すべての試行と
失敗を記録する。失敗の性質（入力によるのか、基盤の不具合か、結果と関係するか）の分析は、この計画の範囲外の別の仕事とする。

- やり直し: 状態が成功でない回（タイムアウト、実行エラー、解析エラー、無効）は、同じ入力・同じ seed で、合計 3 回まで実行する
  （`--max-attempts`、既定 3）。成功した最初の試行の結果を、その点の結果とする。
- やり直すのは orchestrator（決定 1）。失敗の記録が届いたら、同じ payload をキューに戻す。別の号機で実行されうるので、号機の不調で
  3 回とも失敗することを避けられる。3.4 の出し直しと同じ仕組みを使う。
- 適用範囲: 統計モード、`--stopping-rule`、AWSIM の GP 探索（`explore` など。決定 3。保証の表示は今どおり「なし」）、
  重点サンプリング（決定 4。今の `--retry-failed` の動きを既定にし、上限を 3 回にそろえる）。
- 記録: 点ごとに、すべての試行（試行番号、状態、失敗の理由、所要時間、ワーカー、時刻）を記録に残す。成功した点でも、それまでの失敗の
  試行を残す。3 回とも失敗した点は「解決しない点」として、入力とともに記録する。試行ごとの行は記録の JSONL に残し、dataset CSV には
  試行番号の列を足す。統計の計算には、各点の最後の試行だけを使う。
- 番号: ケースを発行した時点で固定の番号（`sample_index`）を付け、順序の判断とやり直しの対応付けに使う。キューが取り出し時に付ける
  `global_loop_num` は、やり直すと別の番号になるので使わない（AWSIM の探索にも `sample_index` を付ける）。
- 統計の扱い: 3 回とも失敗した点は、今と同じく推定から除く（既定 `exclude`。数値は今と変わらない）。そのかわり、報告に次を必ず出す。
  - 解決しない点の件数と割合、やり直しで成功した点の件数（何回目で成功したか）
  - 解決しない点が 1 件でもあれば、保証の表示を「近似」に下げる
  - 参考として、解決しない点を 0 とした場合と 1 とした場合の区間（`binary` の指標のみ。Horowitz & Manski 2000 の両端の区間）。
    判断（停止）には使わず、報告だけに出す
- 範囲外: 失敗の原因の分類、汚染（落ちずに間違った結果を返す回）の検査、走行の質の検査、実行できる入力の式。
  分析の材料として、上の記録を残すところまでを行う。

### 3.4 失われたケースの出し直し（D）

- orchestrator の外部ワーカーの経路に、重点サンプリングの実行器と同じ規則を入れる。ワーカーが受け取ってから
  `--case-timeout` 秒たっても完了しないケースを、同じ payload（同じ番号・同じ seed）で出し直す（`--max-attempts` まで）。
- `--case-timeout` の既定（決定 2）: 新しい倍率は設けず、すでに手で試して余裕を持たせてある既存の数値を使う。
  - AWSIM: そのシナリオの `TIMEOUT_SEC`（U ターン 300 秒、ほか 200 秒）に、既存の準備・後処理の時間（AWSIM の起動待ち
    `initial_warmup_sec` 40 秒、`extra_refresh_warmup_sec` 15 秒、起動確認 `refresh_probe_timeout_sec` 45 秒、
    `post_timeout_grace_sec` 10 秒）を足したもの（U ターンで 410 秒）。ワーカーが受け取ってからの時間で測るため、シミュレーション
    以外の時間も含める必要がある。どれも既存の既定値で、新しい値は足さない。
  - 手元で実行する dynamics・PRISM・bernoulli: なし（失われることがないため）。
  - 重点サンプリングのクラスター実行（今の既定 1,800 秒）も、AWSIM では同じ値にそろえる。
- 同じ番号の記録が 2 つ届いても、3.1 の重複の扱いで最初の 1 つだけを使う。
- 出し直しを使い切ったケースは「失われた」として完了扱いにし、orchestrator が終わらない問題も解消する
  （`completed >= dispatched` の判定で、失われたケースを完了に数える）。

## 5. 決めたこと

| 項目 | 決定 |
|---|---|
| 失敗の扱い | 式は使わない。同じ点で 3 回まで実行し直し、すべての試行と失敗を記録する。解決しない点は除き（数値は今と同じ）、件数と両端の区間を報告し、保証の表示を「近似」に下げる。失敗の性質の分析は別の仕事 |
| 1. やり直す場所 | orchestrator がキューに出し直す（別の号機で実行されうる） |
| 2. 失われたケースの判定時間 | 既存の既定値を使う。AWSIM はシナリオの `TIMEOUT_SEC` と既存の準備・後処理の時間の和（U ターン 410 秒）。手元実行の対象はなし |
| 3. AWSIM の GP 探索 | やり直しと記録を使う。保証の表示は「なし」のまま |
| 4. 重点サンプリング | 既定で 3 回までやり直す（統計モードにそろえる） |
| 5. 宣言の外の値 | 区間を出さずにエラーで止める（EBStop で先に入れた扱いに統一） |
| D（出し直し） | 入れる（やり直しと同じ仕組み） |
| AWSIM の `min_ttc` に EBStop を使うか | 使わない（2026-11-01 決定）。`min_ttc` には上限がなく（無限大を含む。U ターンのデータ 2,830 件で約 34% が既定の範囲 0〜10 秒の外）、EBStop の保証が成り立たないため。先行して実装した（`3929a02`）: 範囲のない指標の宣言（`unbounded_metrics`）と実行前のエラー、EBStop の評価での範囲外の値の検査。分布・分位点は DKW、危険な回の割合は 0/1 の指標と二項区間で扱う。理由の詳細は [statistical_method_selection.md](statistical_method_selection.md) の EBStop の節 |
